# 盐憩项目展示提纲

> 长版说明已经整合进 [README.md](../README.md)。
> 这份文件保留答辩时最常用、最容易直接拿来讲的路线和问答口径。

## 1. 开场一句话

盐憩是一个潜水旅游主题的品牌化前端项目。它不是普通旅游信息站、电商预订页或后台表单，而是把“进入海、理解海、把海收进行程”做成连续海层体验的网站。

## 2. 展示时先讲什么

先讲定位，不要先讲功能。

推荐开场顺序：

1. 盐憩为什么不是普通旅游网站。
2. 页面为什么按海层关系组织。
3. 首页、详情页、行程页分别解决什么体验问题。
4. 最后再讲技术实现和本地状态。

可以直接说：

这个项目不是把页面当成功能栏目平铺，而是把它们理解成同一片海里的不同深度。用户从静水门厅进入首页，再进入具体海域，最后把海域收进行程。

## 3. 页面层级关系

- `index.html`：潜前门厅 / 静水入口。
- `home.html`：海面第一层，负责看海、选海和建立品牌第一印象。
- `detail.html`：进入具体海域，负责 Sea Dossier、Sea Atlas、Dive Brief 和下潜回声。
- `trip.html`：更深一层的规划空间，负责 Planner Desk、已收进行程和 Sea Brief。
- `contact.html` / `terms.html` / `privacy.html`：更浅、更静的说明水域，不退回普通文档页。

## 4. 推荐演示路线

### 第一段：从门厅进入

页面：`index.html`

讲点：

- 这页不是普通登录页，而是潜前门厅。
- 登录、注册和“带上一段航线”都被收在静水入口里。
- “带上一段航线”适合展示时直接进入完整主线。

建议操作：

- 点击“带上一段航线”，进入 `home.html`。

### 第二段：展示首页海面第一层

页面：`home.html`

讲点：

- 首页不是搜索页，而是海面入口。
- 今日海域负责第一眼吸引，海域陈列负责慢慢展开目的地。
- Dive Match 不是普通筛选器，而是根据证书、经验和身体节奏判断更适合的海。
- 下滑时可以顺带指出深度计变化，说明页面不是普通滚动，而是在海层里移动。

建议操作：

- 切换今日海域卡片。
- 点击一个海域进入详情页，或者直接打开 `detail.html?id=7`。

### 第三段：重点展示详情页

页面：`detail.html?id=7`

讲点：

- 详情页不是普通景点详情页，而是深海海域档案。
- Sea Dossier 负责读懂海域。
- DIVE READINESS 负责证书和近期下潜判断。
- Sea Atlas 是核心技术展示点：本地离线海图、潜点、出发点、靠近路线和全屏查看。
- Dive Brief 不是购买栏，而是当前这一程的潜水简报。
- 下潜回声和相邻海域让页面不像商品详情，而像一片海被继续阅读。

建议操作：

- 滚到 Sea Atlas。
- 点击“放大全屏海图”，再按 `Esc` 返回。
- 点击右侧“展开这套安排”，说明它是潜水简报，不是电商下单。
- 可选择“收进行程”，进入 `trip.html`。

### 第四段：展示行程页三段关系

页面：`trip.html`

讲点：

- 行程页不是普通表单页。
- Planner Desk 负责编辑草稿。
- 已收进行程负责切换已经确认的海域。
- Sea Brief 负责查看当前这一程的最终摘要。
- 这三段关系让用户知道自己是在写草稿、收住海域、查看简报。

建议操作：

- 如果已经从详情页收进行程，就展示当前 Sea Brief。
- 如果是空状态，就说明 Planner Desk 会先展开，引导用户慢慢把海域、日期和同行写进去。

### 第五段：快速带过信息页

页面：`contact.html`、`terms.html`、`privacy.html`

讲点：

- 信息页没有做成普通文档页。
- 联系页是联络水域，留言叫站内留言回声，会先保存在当前浏览器。
- 协议和隐私页用潮线目录和说明壳体保持主站气质。

## 5. 汇报时最值得强调的系统

### 深度计系统

- 不是装饰。
- 是整站空间语言。
- 负责页面深浅关系、滚动深度和跨页语义。

### 页面过渡系统

- 不是普通 fade。
- `index -> home` 像从岸上进入海面。
- `home -> trip` 是继续下潜。
- `trip -> home` 是缓慢上浮。
- `detail -> detail` 是相邻海域之间潜游。

### Sea Atlas

- 不是截图占位。
- 使用 Leaflet 和本地离线地图包。
- 能展示潜点、出发点、靠近路线和水下结构。
- 支持 inline 查看、全屏探索和 `Esc` 返回。

### Planner Desk 与 Sea Brief

- Planner Desk 负责写草稿。
- 已收进行程负责收住确认过的海域。
- Sea Brief 负责把当前这一程整理成摘要。
- 这套关系避免行程页变成普通订单表单。

### 本地状态系统

- 项目是纯前端站点，没有接后端。
- `localStorage` 和 `sessionStorage` 用来维持体验连续性。
- `YANQI_PLANNER_DRAFT` 保存 Planner Desk 草稿。
- `YANQI_CONFIRMED_BOOKINGS` 保存已收进行程。
- `YANQI_CONTACT_MESSAGES` 保存站内留言回声。
- `yanqi-trip-store.js` 负责详情页和行程页之间的共享状态。

## 6. 如果老师问“你的创新点是什么”

可以这样回答：

1. 我没有把它做成普通旅游站，而是先定义品牌世界观，再让页面和功能从这个世界观里长出来。
2. 页面不是平级切换，而是海层关系，所以视觉、滚动、深度计和跨页动效都能统一。
3. Sea Atlas 不是普通地图占位，而是本地离线海图系统，能把具体海域结构展示出来。
4. 行程页不是普通表单，而是 Planner Desk、已收进行程和 Sea Brief 三段式规划体验。
5. 我关注的不只是功能能不能用，还关注每个模块是否仍然像盐憩，而不是退回普通网页组件。

## 7. 如果老师问“技术上你做了什么”

可以从五层回答：

- 结构层：多页面 HTML 按页面职责拆分。
- 样式层：CSS 统一深海蓝、海盐白、玻璃感、雾感和微光。
- 交互层：原生 JavaScript 负责卡片切换、浮层、滚动、地图、行程写入和页面状态。
- 空间层：`depth-manager.js`、`depth-gauge.css`、`page-transition.css` 共同管理深度计和跨页过渡。
- 状态层：`localStorage`、`sessionStorage` 和 `yanqi-trip-store.js` 负责跨页数据延续。

## 8. 如果老师问“项目难点在哪”

可以这样回答：

1. 难点不是单个功能，而是所有模块都不能退回普通网页范式。
2. 深度计、跨页过渡和页面深浅关系必须统一，否则项目会碎掉。
3. 详情页既要有大量信息，又不能像商品详情页或文档页。
4. Sea Atlas 要保持技术展示感，同时不能破坏深海安静气质。
5. Trip 页要让 Planner Desk、已收进行程和 Sea Brief 职责清楚，不能变成普通表单或订单流程。
6. 没有后端时，仍要用本地状态把跨页体验接住。

## 9. 如果老师问“为什么没有接后端”

可以这样回答：

这个项目当前定位是前端展示与交互叙事。我把重点放在页面体验、跨页状态、Sea Atlas、深度计和规划链路上。为了保持展示完整性，我用本地存储模拟用户草稿、已收进行程和站内留言回声。后续如果继续扩展，可以把这些状态接到后端，但这次答辩重点是前端体验闭环。

## 10. 如果老师问“有没有不足”

可以这样回答：

有。当前项目主要做桌面端展示，移动端不是本轮重点；另外部分海域素材和评论内容仍然可以继续补充。如果后续继续做，我会优先补真实内容素材、完善 Sea Atlas 的更多海域数据，再考虑后端账户和真实预订流程。

## 11. 收尾句

可以直接用这句：

盐憩想表达的，不只是“哪里可以潜水”，而是“怎样让用户在浏览、选择和规划之间，慢慢进入一片更适合自己的海”。所以我把页面、视觉、动画、地图和本地状态都收进同一套海层叙事里，让它不像普通旅游站，而像一个完整的潜水品牌前端作品。
